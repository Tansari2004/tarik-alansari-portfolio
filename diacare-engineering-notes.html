& test summary

A sanitised account of the behaviour behind the application screens.

Verification date: October 24, 2026 · Local implementation

Verification status

22 focused tests passed across six existing test files. The run used Flutter’s test runner with mocked preferences and secure storage where required. It did not use production accounts, patient data, or production services.

The checks below combine direct behavioural tests and source-contract assertions. A contract assertion checks that an implementation path contains the expected calls; it is weaker evidence than executing the complete flow on a device.

Behaviours inspected

  1. Photo cancellation — 3 tests. Cancelling ends the interface’s wait before the request completes; normal completion still returns a result; a late request error after cancellation is handled. This does not demonstrate remote request termination.
  2. Shared analysis deadline — 3 tests. A completed stage returns, a stalled stage times out, and later stages share the first stage’s time budget.
  3. Portion conversion — 4 tests. Confirmed item weight and count determine grams; liquid volume is not silently treated as weight; a known reference supports food-specific conversion; invalid references do not produce a loggable portion.
  4. Local-data cleanup — 4 tests. Account cleanup removes known and newly added account preferences while preserving approved device settings; it detects legacy account data, resets registered in-memory state, and supports explicitly retained account-owned profile data.
  5. Identity ownership — 6 tests. Cached identity and role are checked against the active account; a matching email cannot override a different owner ID; same-account identity remains available, and a signed-out session cannot use an account-name cache.
  6. Normal logout — 2 tests. A session-state fixture retains account data until explicit account cleanup. A source-contract check confirms that normal sign-out flushes pending plan synchronisation, stops medication reminders, and avoids destructive account cleanup.

Shared meal state: source review

The meal-log repository is documented and implemented as the shared source for planner and manual-log entries. Entries retain base nutrient values, portion multipliers, and nullable optional nutrients. This supports consistent entries and avoids repeatedly scaling already-adjusted values.

The 22-test run did not directly prove full planner-to-log synchronisation or repeated nutrient-edit behaviour end to end. The portion tests above exercise conversion rules, not the entire meal editor. Those workflow-level checks remain distinct from this focused evidence.

Evidence boundaries

This note is a summary of a local run and source inspection, not independently reproducible public source evidence or a security audit. It does not establish Firebase access-rule enforcement, real-device sign-in and notification behaviour, recognition accuracy, usability, clinical effectiveness, or performance of a released build.

Normal sign-out retains the returning account’s data. A different account triggers account-scoped cleanup and ownership checks; approved device preferences can remain. Retention and isolation are separate behaviours and should not be described as deleting all data on every logout.
