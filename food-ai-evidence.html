Historical model comparison

The published aggregate JSON preserves the saved CLIP/SigLIP comparison. Both rank the same 2,356 names. Food-presence classification is bypassed; nonfood images are excluded. The two samples are 294 app food assets and 202 Food-101 validation photos.

The Food-101 sample selects two photos per category at dataset-viewer offsets category_block * 250 + 17 and the following row. Accepted names are compared using exact or reviewed spelling normalisation; valid singular/plural variants and alternative names may still be counted as misses. The catalogue has exact normalised names for 84 of the 101 benchmark categories.

CLIP top-1/top-3/top-6 matches were 67/112/137 of 202. The tested SigLIP configuration returned 47/64/77 matches. The candidate is google/siglip2-base-patch32-256, pinned to revision 94dffa8cb1179de3e03f091dbc3917e5d5a9ae84. Results supported retaining CLIP over this tested SigLIP configuration. Selection against the open-ended provider remains unresolved; a shared evaluation of the full confirmation workflow is still needed.

These samples informed model selection. App assets also informed earlier tuning. Neither is a fresh representative DiaCare final test set. Local timing excludes upload, cold start, and model initialisation. The underlying benchmark images and per-image research manifests are not published here, so the aggregate file alone is not sufficient to independently reproduce the experiment.

Separate open-ended naming experiment

The saved October 3 experiment used 202 Food-101 photos plus five nonfood and two egg fixtures, making 209 requests. The first accepted name matched on 115/202 photos (56.9%); any returned name matched on 124/202 (61.4%). Thirteen requests failed—11 read timeouts and two other request failures—and were counted as misses without retries.

Open-ended component names and ranked alternative dish names are different outputs. These match rates do not measure human-reviewed semantic correctness, portion accuracy, or nutritional accuracy. A separately configured test service was recorded, but the native signed-in camera round trip remained unverified. No new provider requests or deployment changes were made for this portfolio update.

Recorded example and provenance

The published boiled-egg image is the app’s development fixture, not a user photo. The October 3 saved open-ended evaluation records exactly two labels for it: “hard-boiled egg” and “egg”. These fields are preserved in the prediction-example JSON.

The contemporaneous research note records “hard boiled eggs” at rank 2 for CLIP on the same fixture. It does not preserve the full ordered prediction list, scores, or the first-ranked name. The report therefore shows that the specific accepted match was second without inventing a wrong first label. No fresh inference was run for this example.

The correction and final-confirmation steps on the report are explicitly illustrative. There is no recorded user correction, serving, or final log for this fixture. It demonstrates why review is available, not that users performed it successfully or saved time.

Backend verification · 35 tests passed

The local command was python -m pytest -q food_vision_api. Existing test modules cover API/image boundaries, catalogue mappings, ranking, evaluation accounting, model-comparison accounting, optional-provider parsing, and provider failure handling.

Fixtures and mocks avoid downloading model weights, making paid inference requests, or uploading real photos. Authentication coverage checks rejection without credentials; it does not establish all Firebase access-control behaviours. Fake image rankers exercise response paths, not recognition quality. A missing local test dependency was installed before the complete passing run.

Flutter verification · 38 focused tests passed

The run used flutter test --no-pub with these six existing files under test/:

  • food_photo_recognition_service_test.dart — scored/unscored parsing, confirmation flags, uncertain and nonfood responses, malformed values, and readiness warm-up.
  • photo_capture_flow_test.dart — rapid taps, consent cancellation, camera failure, retry, and waiting for the consent-dialog transition.
  • photo_analysis_status_card_test.dart — loading, rejection, cancellation, distinct retry/new-photo controls, and manual search in English and Arabic.
  • photo_analysis_deadline_test.dart — completed, stalled, and shared-budget stages.
  • photo_analysis_cancellation_test.dart — immediate cancellation, normal completion, and late errors.
  • portion_estimate_test.dart — confirmed reference calculations, volume/weight distinction, and invalid inputs.

The local runner reported successful completion. These are helper and widget checks, not an end-to-end device camera, authenticated production upload, or released-app verification.

Evidence boundaries

This is a sanitised summary of private implementation and saved research records. It does not publish production code, user images, credentials, or private logs. The October 3 comparison was inspected and its count arithmetic checked, but model inference was not rerun on October 24.

Precomputed embeddings and ONNX are implementation choices, not evidence of a speed or memory improvement without a controlled before/after benchmark. The practical next evidence is a reserved camera-photo evaluation set with independent labels, plus a signed-in device workflow check. Provider retention, calibration, food coverage, and any health outcomes require their own evidence.
